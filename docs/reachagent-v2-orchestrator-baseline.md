# ReachAgent V2 Orchestrator baseline

Audit date: 15 September 2026 (Australia/Sydney)

Scope: isolated V2 branch and local/synthetic V2 environment. This document was completed before Orchestrator implementation. No production application, database, data, Trigger.dev task, provider, or deployment was accessed or changed.

## Executive finding

The active workflow is a serial, batch-oriented Trigger.dev task. `trigger/daily-pipeline.ts` owns the order Finder → Researcher → Writer → Sender → Follow-up → Reactivation. Per-lead decisions are partly centralized in the Decision Engine, but batch selection, sequencing, executor calls, failure boundaries, and re-evaluation remain distributed. The existing executor internals already contain important safety behavior—quotas, recipient claims, durable send intent, send-time suppression checks, provider idempotency, and stage-specific locks—that must remain in those executors.

The required incremental boundary is therefore:

1. Trigger.dev retains schedule, queue concurrency, task retry, duration, and Finder.
2. A bounded selector supplies existing lead IDs; the Orchestrator never discovers or scans an unbounded population.
3. The Orchestrator loads one lead's Decision Context, invokes the pure Decision Engine, dispatches exactly one mapped lead-scoped executor, reloads durable state, and repeats within a hard limit.
4. Existing batch agents remain the default path while `ORCHESTRATOR_ENABLED=false`.
5. Shadow mode evaluates and records intended work without calling an executor.

## Current stage order and failure boundaries

The active order is fixed in Trigger code, not inferred dynamically:

`Finder → Researcher → Writer → Sender → Follow-up → Reactivation`

- Finder 402 is fatal. Other Finder/Researcher/Writer/Sender failures are recorded as partial and Follow-up still runs.
- Follow-up or Reactivation failure fails the daily task.
- Finder runtime exhaustion skips Researcher/Writer/Sender but still runs Follow-up/Reactivation.
- Each batch stage discovers its own population from durable status. There is no workflow checkpoint beyond durable business state and Prompt 10 observability.
- Trigger retries the task; stage replay safety relies on durable lead/email state, per-lead generation locks, sender lock, recipient claims, unique pending/delivered intent constraints, and stable provider idempotency derived from email row IDs.

The Orchestrator must not emulate those stage-level failure policies. For one lead it stops on the first executor failure and returns retryability; Trigger remains responsible for whether/when to retry. A bounded batch helper may isolate results so one lead failure does not reject the whole batch.

## Locks, quotas, and flags

- Whole daily run: `daily_pipeline` database lock plus Trigger queue concurrency 1.
- Initial generation: `initial-email-generation:<leadId>` lock.
- Initial sending: `sender_agent` database lock across quota check and sends.
- Recipient ownership: atomic database claim shared by initial, follow-up, and reactivation paths.
- Follow-up/reaction replay: one durable email intent per lead/type with provider idempotency derived from its UUID.
- Reactivation quota: currently safe only under the serialized daily pipeline; a new callable lead executor must preserve a serialized quota boundary.
- Existing gates: `OUTREACH_SEND_ENABLED`, `TRIGGER_JOBS_ENABLED`, `FINDER_SCHEDULE_ENABLED`, `HOSTINGER_MUTATIONS_ENABLED` all default false in V2.
- New gates must be `ORCHESTRATOR_ENABLED=false` and `ORCHESTRATOR_SHADOW=false`. Shadow takes precedence over enabled execution and cannot call an executor.

## Audit gate

The required coordination sources have been inspected: daily Trigger sequencing, Finder, Researcher, Writer, Sender, Follow-up, Reactivation, inbound reply handling, manual/API execution, run-all behavior, ordering, retry boundaries, locks, quotas, flags, Decision Engine integration, and Observability integration. The baseline identifies what moves into the Orchestrator and what remains in Trigger.dev or executor services. Implementation may proceed.
